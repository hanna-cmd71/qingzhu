# 青竹剑阵 v2.0 需求文档（草案）

状态：**需求已确认（2026-09-21）· 尚未实现**

实现进度：WP0 前置改造（P1 武器图集解耦、P2 剑数配置驱动）已完成并验证；WP1 及之后尚未开始。

本文档定义 2.0 的功能范围、边界与验收要求。文档中的一切内容均为计划；未落地的部分不得写入游戏内帮助、游玩说明或更新日志，也不得在验收报告中表述为已实现。

阅读顺序建议：先看第 1 节确认目标与排除项，再看第 3 节前置改造与第 8 节里程碑确认实施顺序，最后处理第 10 节的待决事项。

---

## 1. 背景与目标

### 1.1 现状（1.0）

- 当前版本 1.0，篇名「虚天殿篇」，玩家固定操作韩立，御使七十二口青竹蜂云剑。
- 六种起手（御剑、雷法、傀儡、御虫、符阵、护身）构成玩法身份，同时决定叙事包装与界面配色。
- 遗物 36 件、战术核心 12 件，合计装备 48 件；遗物同时最多 6 件，核心最多 2 件。
- 表现资源集中在 9 张图集，人物与武器外观共用同一张 `hanli-sword-atlas`。
- 存档格式 1，键 `fanren-qingzhu-v1`，records schema 1；成绩规则分组维度为固定的十项 `RULE_KEYS`。

### 1.2 v2.0 目标

在不改变玩家身份设定（韩立）、不改变主篇叙事的条件下，扩展玩家的自我表达与战斗手段：

1. **时装系统**——让玩家在同一身份下替换外观，并把元进度从"修持与成就"扩展到"外观收集"。
2. **武器系统**——把当前隐式的青竹蜂云剑显式化为可选择的「御剑法门」，使不同的剑阵调度方式成为可玩维度。
3. **流派技能**——给六个现有起手各增加一个主动技能，使战斗从"通用神雷加剑式切换"扩展为每流派拥有自己的主动手段。

### 1.3 明确排除

- 不新增可选操作人物。玩家身份保持韩立，主篇叙事、过场与人物关系不变。
- 不更换篇名 `GAME_ARC`，不引入虚天殿篇之外的角色与事件。
- 不新增货币、不改变存档格式、不改变 records schema。
- 不给时装附加任何战斗属性。
- 不让武器与流派技能进入成绩分组维度。
- 不新建独立攻击系统（见 5.2 武器深度）。

| 维度 | 表现平面 | 规则平面 |

## 3. 前置改造（P）

以下两项不产出玩家可见功能，但时装与武器均依赖它们，必须先行完成。

### P1 飞剑外观与人物图集解耦

现状证据：`game/gameplay/art.js` 中人物帧分配为 `0` 静止、`1` 朝上、`2` 朝左、`3` 朝右、`4`/`5` 朝下行走两帧、`6` 神雷姿态、`7` 为飞剑贴图；飞剑绘制直接读取 `this.art.heroes[7]`，闪避残影读取 `heroes[0]`。

问题：人物姿态与武器贴图共处一张 4×2 图集。时装若替换整张图集，会连带替换飞剑外观；武器若更换外观，则要求重画整张人物图集。两个系统被强行绑定。

要求：

- 新增独立武器图集，承载飞剑外观；`heroes[7]` 不再作为飞剑绘制来源。
- 人物图集收敛为纯姿态资源，切分规则不变。
- 残影、神雷姿态等既有表现保持不变。

验收：切换时装不影响飞剑外观；切换法门不影响人物姿态；两种操作均不改变战斗结果与随机数序列。

### P2 剑数由配置驱动

现状证据：`game/gameplay/engine.js` 中 `syncSwords()` 使用 `Math.min(72, this.level)`，剑数量是等级的纯函数，中间没有可配置入口。

要求：

- 剑数量改为"配置驱动、等级兜底"：法门可声明剑数规则，缺配置时回落为 `min(72, level)`。
- 等级派生状态的对账逻辑保持单一入口，不新增第二处同步点。
- 快照校验继续先比飞剑数量与等级、再比派生上限的顺序语义。

验收：不携带法门配置的旧快照恢复后行为与原实现一致；携带法门的新局剑数可被快照校验接受。

## 4. 时装系统

### 4.1 功能需求

- 时装为账号级收集项，跨模式、跨局、跨难度生效。
- 提供时装列表与预览：在出发页或洞府内可查看全部时装的解锁状态与外观，并切换当前装配。
- 时装切换为纯表现，切换后立即生效，不需要重开本局。
- 战斗中的切换入口需暂停并清除输入，遵守现有暂停语义。

### 4.2 数据与存档

- 新增账号级字段：已解锁时装清单与当前装配，命名遵循项目既有风格。
- 参照药园 `garden` 先例：字段后加、由 `normalizeSave` 补齐默认、旧档缺字段回落为默认时装。
- 存档格式 1、键 `fanren-qingzhu-v1`、records schema 1 保持不动。
- 时装状态不进入本局 `checkpoint` 快照，避免中途换装污染快照校验。

### 4.3 表现与美术

- 覆盖范围：战斗姿态帧与对话立绘；菜单头像与过场立绘是否纳入待定（见第 10 节）。
- 载体优先级：配色与部件覆盖优先，全新图集作为后续加量手段。
- 时装不得消费战斗随机数，不得改变时间、镜头、奖励或飞剑行为。
- 每套时装资产须走完整管线：PNG 原图 → 编码 WebP → 更新 `public/assets/encoded/manifest.json` 哈希 → 双离线构建（WebP 与 PNG 兼容版）。

### 4.4 获取与解锁

- 解锁条件复用现有机制，优先挂在成就体系上；不新增货币。
- 解锁判定的依据必须来自本机真实数据，不得凭章节或账号历史补发。
- 解锁状态一旦达成不可回退，进入恢复流程时与被保护记录同等对待。

### 4.5 验收标准

- 新档、旧档、损坏档三种情况下时装字段均能正确回落或保留。
- 切换时装前后，同一固定种子的战斗结果逐字节一致。
- 图鉴与成就页面正确区分"已解锁"与"未解锁"，不产生重复奖励。
- 触屏与键鼠两种输入下均可完成切换。

## 5. 武器系统（御剑法门）

### 5.1 定位与叙事边界

武器不替换青竹蜂云剑本体，而是同一批七十二剑的不同调度法门。

理由：整篇虚天殿篇的前提是七十二剑已在乱星海炼成，替换本体将推翻开局设定；同时项目约定要求区分"持有器物"与"战场配置"，法门属于后者。

### 5.2 功能需求

- 提供 3 至 4 把法门，全局可选，不限定起手。
- 每把法门具备明确的调度特征，例如少而强、多而弱、穿透优先、定点压制。特征须能在一句话内向玩家说清。
- 法门为独立槽位，不占用现有 6 格遗物位与 2 格核心位。
- 获取途径复用现有整备、经济与节点回执体系，不新增商店与货币。
- v2.0 不做法门升级与精炼。

**深度边界**：法门改变剑阵的被动与持续形态（伤害构成、索敌策略、穿透、数量、调度方式），复用现有飞剑循环；**不接管攻击形态本身**，不新建独立攻击系统。

### 5.3 规则与门控

- 新增子版本号（暂名 `weaponVersion`），与 `balanceVersion`、`growthVersion` 等既有子门控同构。
- 新局启用；缺标记的旧局按旧默认恢复，绝不在续玩时静默升级。
- `rulesVersion` 保持 3，不新建引擎族。
- 法门选择进入本局快照，并纳入快照校验；非法或越界配置必须在写入前被拒绝。
- 存档校验只接受合法法门 ID，缺失按默认回落。

### 5.4 平衡要求

- 必须重跑 `npm run test:balance` 固定策略模拟。
- 覆盖矩阵至少包含三档难度 × 六流派 × 每把法门，使用 `BATTLE_PATHS` 环境变量扩展流派维度。
- 自动策略胜负不作为真人胜率证据；全部失败样本保留。
- 法门造成的数值差异须控制在可回调范围内，特征差异优先于纯数值差异。

### 5.5 表现

- 每把法门需要独立外观，取自 P1 建立的武器图集。
- 法门切换与生效不得消费战斗随机数中的表现部分。
- 剑阵相关的既有表现（七十二剑演示、剑式切换提示）须与法门特征保持一致，不得出现文案与实际行为矛盾。

### 5.6 验收标准

- 携带法门的新局在快照往返、暂停、恢复后行为一致。
- 缺 `weaponVersion` 的旧局恢复后与 1.0 行为逐字节一致。
- 六流派 × 每把法门的固定策略模拟完成并留存证据。
- 整备界面正确展示法门槽位，替换与购买流程遵守既有确认与备份约定。

## 6. 流派技能

### 6.1 定位与边界

流派技能承担"主动释放"职责，武器承担"被动与持续形态"职责。两者不得重叠：任何效果都必须能明确归入其中一侧，否则不纳入本版本。

- 每个现有起手新增 1 个主动技能，共 6 个。
- 技能属于起手，不随法门变化。

### 6.2 功能需求

- 资源体系复用现有灵力与雷源，不新增资源种类。
- 每个技能具备明确的冷却或消耗，并在界面上可见剩余状态。
- 技能效果须与该起手既有机制形成配合，而非独立并行：例如御剑的聚锋、符阵的留符、护身的反击各自应有可衔接的主动手段。
- 新增技能须在出发页与洞府中有对应说明，文案由真实规则函数生成，不得手抄数值。

### 6.3 输入与触屏约束（关键）

现状证据：`game/gameplay/keybindings.js` 的 `DEFAULT_KEYS` 现有五个可绑定动作（闪避、神雷、剑式、物资 1、物资 2）。

要求：

- 新增一个动作槽位 ID，纳入设置页绑定与冲突校验；沿用合并语义，保证旧键位记录不被静默改写。
- 触屏端新增按钮须在 390×844 视口下满足既有验收断言：战场占比不低于 55% 视口高度、摇杆距底不超过 180px、既有技能按钮保持可见。
- 若无法同时满足，须显式调整验收断言并说明原因，不得降低标准后静默通过。
- 暂停、悟道、整备、帮助、确认、设置、失焦与离开战斗时清除技能输入与缓冲，与现有闪避缓冲语义一致。

### 6.4 门控与平衡

- 新增子版本号（暂名 `skillVersion`），策略与 5.3 一致。
- 与武器同批验证，共用一次平衡验证周期。
- 技能不得重复结算、不得截断遗忘凭据；结算须有唯一凭据。

### 6.5 验收标准

- 六个技能在固定策略模拟中均被实际触发并产生预期效果。
- 键鼠与触屏均可释放；键位冲突与恢复流程正确。
- 技能不改变表现层随机数与声音播放以外的任何既有规则语义。

## 7. 跨系统约定

### 7.1 版本策略

- `GAME_VERSION` 升至 2.0，包版本 2.0.0，发布标签 v2.0，产物进 `release/2.0/`。
- `GAME_ARC` 保持「虚天殿篇」不变。
- `rulesVersion` 保持 3；新增 `weaponVersion` 与 `skillVersion` 两个子门控。
- 各系统版本以所属源码常量为准，不共用游戏显示版本。
- 1.0 存档在 2.0 中必须可继续游玩，不得清档、补造成绩或转换旧局。

### 7.2 存档与兼容

- 存档格式 1、键 `fanren-qingzhu-v1`、records schema 1、十项 `RULE_KEYS` 全部保持。
- 新增字段必须可由 `normalizeSave` 校验，旧档缺字段按各系统既有默认恢复。
- 覆盖类入口遵守既有约定：先说明影响并确认，保留可恢复前态，写入失败保留原状。

### 7.3 成绩与图鉴

- 武器与流派技能**不进入成绩分组维度**。理由：`RULE_KEYS` 固定十项，新增维度会使 1.0 成绩失去归组依据。
- 后果：同难度、同流派、不同法门的成绩共用同一榜，此取舍须在说明中向玩家交代。
- 时装与法门进入图鉴时，须区分账号历史、本局真实状态与实际配置，不按章节补发。

### 7.4 资源管线

- 原 PNG 与编码 WebP 副本均保留，嵌入前核对哈希，不静默沿用失效编码。
- 重新编码需 Python 3 与 Pillow，执行既有编码脚本并更新 manifest。
- 每次资源变更后重建 WebP 与 PNG 两份离线 HTML。

### 7.5 文档同步

- 玩法、入口、数值、资源、解锁、保存流程或界面提示变更，须在同一次工作中同步根游玩说明与更新日志。
- 说明中的表格由 `npm run docs:tables` 从真实规则函数生成；构建侧只做校验，不修改源文档。
- 更新日志正文由作者指定，不擅自宣布版本状态。
- 新增顶层交付文件须登记到源码白名单。

### 7.6 许可与署名

- 原创代码保持 GPL-3.0-only，保留 SPDX 与版权说明。
- 首页署名保持 `制作人：bilibili@卡布奇诺ultra`。
- 新增素材按既有素材来源文档格式单列，不宣称取得第三方授权。

## 8. 里程碑与实施顺序

已确认拆分为两次发布，使表现平面与规则平面各自拥有独立的验证周期。

| 里程碑 | 内容 | 产出 | 风险 |
|---|---|---|---|
| M0 前置 | P1 图集解耦、P2 剑数配置化 | 无可见功能；解除时装与武器的耦合 | 低 |
| M1 表现批次 | 时装系统 | 可独立发布的 2.0 | 低 |
| M2 规则批次 | 御剑法门 + 流派技能 | 2.1（或与 M1 合并为 2.0） | 中到高 |

M2 的武器与技能必须同批验证。两者都在规则平面，合并成一个验证周期可减少改动叠加后无法归因的问题。

## 9. 风险清单

| 风险 | 说明 | 应对 |
|---|---|---|
| 平衡失效 | 现有平衡经多轮人工与模拟调校，新增规则维度会改变难度曲线 | 独立版本号、完整矩阵模拟、保留失败样本 |
| 触屏空间不足 | 390 宽下需同时容纳摇杆与更多技能键，验收断言为硬约束 | 技能数量收敛为每流派一个；必要时显式调整断言并说明 |
| 美术工期 | 每套时装为姿态帧加立绘，是版本工期的下限 | 先用配色与部件覆盖控制成本 |
| 图集耦合 | 人物与武器共用图集，未解耦会导致两个系统互相绑定 | 将 P1 设为前置，未完成不进入时装与武器开发 |
| 成绩不可比 | 新维度进入分组会使旧成绩无法归组 | 武器与技能不进 `RULE_KEYS`，共用榜单并在说明中交代 |
| 文档与实现脱节 | 说明表格由代码生成，改数值不改文档会导致构建失败 | 数值改动与 `docs:tables` 同次执行 |

## 10. 已确认方案

作者于 2026-09-21 确认按建议默认值执行，以下为冻结结论。后续如需修改，须在此处登记变更并注明日期。

| # | 事项 | 已确认结论 |
|---|---|---|
| 1 | 武器深度 | 参数与被动型，不接管攻击形态（见 5.2 深度边界） |
| 2 | 武器槽位 | 独立槽位，不占用 6 格遗物位与 2 格核心位 |
| 3 | 流派技能资源 | 复用灵力与雷源，不新增资源种类 |
| 4 | 时装覆盖范围 | 战斗姿态帧与对话立绘；菜单头像与过场立绘暂不纳入 |
| 5 | 时装载体 | 配色与部件覆盖优先，全新图集留作后续加量 |
| 6 | 规模数字 | 时装 4 套（1 默认 + 3 解锁）；法门 3 至 4 把；每流派 1 个技能 |
| 7 | 发布划分 | M1 与 M2 分两次发布（2.0 表现批次、2.1 规则批次） |
| 8 | 更新日志正文 | 由作者在发布前指定；在此之前不写入更新日志 |

尚未锁定、留待实现阶段按实际情况决定的事项：

- 时装解锁条件的具体门槛（挂在成就体系上，具体条目在 WP3 中定）。
- 三至四把法门的具体数值与调度特征（WP4 产出候选，数值由作者采纳）。
- 六个流派技能的各自效果（WP6 产出候选，效果由作者采纳）。

## 11. 验收与证据要求

- 自动测试：全部既有用例保持通过；新增时装、法门、技能各自的规则与存档回归用例。
- 浏览器验收：既有验收组保持通过；新增时装切换、法门槽位、技能按钮的界面检查。
- 触屏验收：明确记录操作方式与设备类型。模拟触屏不等于真机手感，真机与单手体验仍待作者验证。
- 平衡验证：留存六流派 × 每把法门 × 三档难度的固定策略输出。
- 存档验证：覆盖新档、1.0 旧档、缺标记旧档、损坏档与并发写入冲突。
- 证据记录须区分自动测试、合成夹具与真人／真机结果。

### 12.3 并行策略与冲突边界

本环境的协作代理共享同一工作目录，并行编辑同一文件会直接冲突。因此分工按**文件与模块**划分，不按功能名义划分。

- **规则平面串行**：WP4 与 WP6 都改 `engine.js`、`expedition.js`、`balance.js` 与快照校验，必须串行推进，或先由一方冻结接口再由另一方接入。
- **表现平面可并行**：WP2 主要改资源与绘制，WP3 主要改 React 面板与样式，文件不重叠，可同时进行。
- **验证独立**：WP9 应在每个工作包完成后独立执行，不与实现工作包共用同一轮判断。
- **建议并发**：同时最多两个实现工作包加一个验证工作包。并发过高会放大冲突，反而拖慢进度。
- **跨工作包改动**：任何工作包若需要修改不属于自己的文件，先在该工作包内说明原因，避免静默扩大改动面。

### 12.4 关键路径

两条并行链路：

- **表现链路**：WP0 → WP1 → WP2 / WP3 → WP9 → WP10
- **规则链路**：WP0 → WP4 → WP5 / WP6 → WP7 → WP8 → WP9 → WP10

关键路径上的外部依赖有两处：时装与法门的美术素材（作者侧，决定 WP2 与 WP5 能否收尾），以及平衡数值的采纳决策（作者侧，决定 WP8 的迭代次数）。这两处是全流程最容易成为瓶颈的环节，宜尽早启动。

### 12.5 单个工作包的完成定义

一个工作包算完成，需要同时满足：

1. 代码改动落在约定范围内，未静默牵连其他模块。
2. 相关自动测试通过，且既有 539 项用例保持通过。
3. 涉及玩法与数值的，说明与更新日志已同步。
4. 涉及界面的，有浏览器验收证据；涉及存档的，有新档、旧档、损坏档三类证据。
5. 证据记录区分自动测试、合成夹具与真人／真机结果。

### 12.6 交付与交接物

每个工作包向下一环节交付：代码改动、对应测试、证据文件、以及受影响的文档更新。规则平面工作包还需交付该系统的版本号常量与回落语义说明，供后续维护与兼容文档登记。
